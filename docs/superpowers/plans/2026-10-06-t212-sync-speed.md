**Goal:** make the first Trading 212 history load finish in roughly 20-40 seconds instead of 2.5 minutes, and stop a stream from being stored as "complete" when Portfyl only read its first page.

**Architecture:** the load is slow because `jobs.broker_backfill_pass` performs ONE `advance_run` step (at most 3 pages per stream) per minutely tick, so 7 order pages cost three ticks. Task 3 makes a single pass keep advancing the same run until it finalizes, hits a rate limit, or exhausts a time budget. Task 4 shortens the local tick so the first step does not wait up to a minute. Task 1 fixes a correctness bug found in the live sync of 2026-10-06 (cash stopped after one page) and makes an unrecognised `nextPagePath` fail the run instead of silently ending the stream. Task 2 fixes a latent rate-limit bug that the drain loop would otherwise expose: `x-ratelimit-reset` is a Unix timestamp, but `parse_rate_limit_headers` reads it as seconds, so the first real 429 would park a run until the year 2083.

**Tech Stack:** FastAPI, SQLAlchemy 2.0, PostgreSQL/Alembic (no migration in this plan), pytest.

**Spec:** `docs/superpowers/plans/2026-09-20-t212-snapshot-first-sync.md` (§5.3 pagination and rate limits, §5.4 continuation job, §5.5 atomic finalization) and `docs/superpowers/plans/2026-10-03-t212-cash-stream.md`. The Trading 212 OpenAPI spec (`https://docs.trading212.com/_bundle/api.json`) is the authority for endpoint parameters and rate limits.

## Evidence this plan is built on (2026-10-06)

- `broker_sync_runs` on the owner's database: audit runs 4-7 each read 304 orders in 142-160 s; incremental runs took 23-63 s. T212 itself would serve 304 orders (7 pages) in about 20 s because each history endpoint allows 20 requests per minute.
- `main.py` drains `broker_backfill` every 60 s (local periodic loop) and Cloud Scheduler calls `/internal/jobs/broker_backfill` every minute (`deploy/cloudrun.md`). `advance_run` is bounded by `DEFAULT_MAX_PAGES_PER_STREAM = 3` per call.
- Run 11 (the first run with the cash stream) staged exactly 50 cash events, marked `cash_complete = true` and set `cash_frontier_at = 2026-10-06`, although the live capture of 2026-10-03 read 250 events over 5 pages (`docs/research/t212-cash-transaction-encoding.md`).
- The OpenAPI spec documents `time` as a query parameter of `/equity/history/transactions` only (orders and dividends have `cursor` and `limit`). `validate_next_page_path` allows only `cursor` and `limit`, so a cash `nextPagePath` carrying `time` is dropped and `_fetch_stream_page` returns `next_path = None`, which `advance_run` reads as "stream finished". The capture CLI (`backend/scripts/t212_capture_cash_transactions.py`) allows `time` and read five pages, which is consistent with this diagnosis. The exact `nextPagePath` shape is not documented, so Task 1 also makes the failure self-diagnosing.

- Rate limits, verified against the official Trading 212 sources on 2026-10-06 (OpenAPI spec `_bundle/api.json` and `https://docs.trading212.com/api/section/rate-limiting`): `/equity/history/orders`, `/dividends` and `/transactions` each allow 20 requests per 1m0s; `/equity/positions` 1 per 1s; `/equity/account/summary` 1 per 5s; `POST /equity/history/exports` 1 per 30s; `GET /equity/history/exports` 1 per 1m0s. Limits are **per account, regardless of API key or IP**, and **bursts are allowed** (the whole quota may be used in the first seconds of the window). Response headers: `x-ratelimit-limit`, `x-ratelimit-period` (seconds), `x-ratelimit-remaining`, `x-ratelimit-used`, and `x-ratelimit-reset`, documented as **a Unix timestamp**. The documentation does not say what a 429 returns beyond the status, and not whether `Retry-After` is sent.
- What is NOT verified: live header values (no 429 has ever occurred in the owner's 11 runs: every `*_rate_limit_reset_at` is null and `retry_count` is 0); how the window slides; whether another app using the same account (for example a second portfolio tracker) already consumes the shared per-account quota.
- Latent bug found while verifying: `t212_sync.parse_rate_limit_headers` (line ~361) computes `now + timedelta(seconds=int(reset))`. With a real Unix timestamp (about 1.79e9) that is 2083-06-27, so `broker_backfill_pass` (which skips a run while `reset_at > now`) would never resume it. The existing tests only use reset values of 5-60, which hide this.

## Global Constraints

- All API IDs stay UUID `public_id`; no migration is part of this plan, so `EXPECTED_ALEMBIC_HEAD` must remain `0022_t212_cash_stream`.
- Tenant isolation: every query the drain loop adds runs after `_set_job_workspace_context(db, workspace_id)`; forced RLS drops the context on every commit.
- Never forward the API key to a URL that failed `validate_next_page_path`.
- Fail closed: an unexpected pagination link ends the run as `failed` with no ledger write and no frontier change.
- Fast suite from `backend/`: `.venv/Scripts/python -m pytest tests/ --ignore=tests/postgres -q`; RED first for every behavior change.
- Do not touch `frontend/` (the history poll already refetches every 5 s while a run is active, `frontend/src/hooks/useT212Sync.js:34`).

## Review Focus

1. A rejected `nextPagePath` on **orders or dividends** used to complete the stream silently; it must now fail the run (Task 1 test `test_unrecognised_next_page_path_fails_the_run_*`).
2. A real 429 carries `x-ratelimit-reset` as a Unix timestamp; the run must resume within about a minute, not in 2083 (Task 2 tests `test_reset_header_is_read_as_a_unix_timestamp` and `test_reset_is_never_further_away_than_the_cap`).
3. A 429 in the middle of a drain must stop the drain and leave the run in `waiting_rate_limit` without a busy loop (Task 3 test `test_drain_stops_when_rate_limited`).
4. Another worker taking the lease mid-drain must stop this pass without finalizing (Task 3 test `test_drain_stops_when_the_lease_is_lost`).
5. A drain must not starve other runs: the time budget is shared across the whole job invocation (every workspace and every run in it), and every run still gets at least one step (Task 3 tests `test_expired_budget_still_gives_each_run_one_step` and `test_all_workspaces_share_one_deadline`). A per-workspace budget would let a cloud request with N active workspaces last N x 40 s and blow Cloud Scheduler's 180 s attempt deadline and Cloud Run's 300 s request timeout.
6. Re-walking cash history after resetting the frontier must not create duplicate cash rows (Task 1 test `test_rewalking_cash_history_in_a_new_run_imports_nothing_twice`, in `test_t212_finalize.py`).
7. The per-account quota can be shared with another app, so a 429 on the very first request of a pass must be handled the same way (Task 3 covers it through the same `waiting_rate_limit` path; Task 5 step 3 checks the live headers).
8. A worker that lost its lease must not mark the run `failed` on a bad pagination link (Task 1 test `test_unrecognised_next_page_path_after_lease_loss_does_not_fail_the_run`).
9. The user sees the pagination-specific message, not the generic "sync failed" one (Task 1 test `test_history_status_shows_the_pagination_error` in `test_broker.py`).

### Task 2: Rate-limit reset is a Unix timestamp; log the headers

**Files:**
- Modify: `backend/t212_sync.py` (`parse_rate_limit_headers` near line 361, the `RateLimitedError` handler in `advance_run` near line 849, `_fetch_stream_page` near line 430)
- Test: `backend/tests/test_t212_sync_runs.py` (next to the existing `parse_rate_limit_headers` tests near line 28, and `TestAdvanceRun`)

**Interfaces:**
- Consumes: `RateLimitState(remaining, reset_at)`, `RateLimitedError(state)`.
- Produces: `t212_sync.RATE_LIMIT_RESET_MIN_SECONDS = 2`, `RATE_LIMIT_RESET_MAX_SECONDS = 120`, `RATE_LIMIT_DEFAULT_WAIT_SECONDS = 60`; `parse_rate_limit_headers(headers, *, now=None) -> RateLimitState` keeps its signature but `reset_at` is now an absolute time clamped to `[now + 2 s, now + 120 s]`; a 429 with no usable reset header waits `RATE_LIMIT_DEFAULT_WAIT_SECONDS`.

Why: Trading 212 documents `x-ratelimit-reset` as "a Unix timestamp indicating the exact time when the limit will be fully reset". The current code adds the value to `now` as seconds, so the first real 429 would produce `reset_at = 2083-06-27` and `broker_backfill_pass` would skip the run forever. Small values (5-60, as in the existing tests) are still read as relative seconds so nothing that passes today breaks. The clamp bounds the damage of any future misreading; the 2-60 s windows of the documented limits fit inside it. Deliberate behavior change: a relative value above 120 (for example 3600, which the current code would honor as one hour) is now cut to 120 s. If T212 really meant a longer wait, the run simply gets another 429 and waits again; that costs one request, while honoring a misread value could park a run for hours.

```python
class TestRateLimitResetHeader:
    NOW = datetime(2026, 10, 6, 12, 0, 0, tzinfo=timezone.utc)

    def _state(self, reset):
        return t212_sync.parse_rate_limit_headers(
            {"x-ratelimit-remaining": "0", "x-ratelimit-reset": str(reset)}, now=self.NOW,
        )

    def test_reset_header_is_read_as_a_unix_timestamp(self):
        reset = int((self.NOW + timedelta(seconds=42)).timestamp())
        assert self._state(reset).reset_at == self.NOW + timedelta(seconds=42)

    def test_reset_header_in_milliseconds_is_accepted(self):
        reset = int((self.NOW + timedelta(seconds=42)).timestamp()) * 1000
        assert self._state(reset).reset_at == self.NOW + timedelta(seconds=42)

    def test_small_values_stay_relative_seconds(self):
        assert self._state(30).reset_at == self.NOW + timedelta(seconds=30)

    def test_a_large_relative_value_is_capped(self):
        assert self._state(3600).reset_at == self.NOW + timedelta(
            seconds=t212_sync.RATE_LIMIT_RESET_MAX_SECONDS
        )

    def test_reset_is_never_further_away_than_the_cap(self):
        far = int((self.NOW + timedelta(days=30)).timestamp())
        assert self._state(far).reset_at == self.NOW + timedelta(
            seconds=t212_sync.RATE_LIMIT_RESET_MAX_SECONDS
        )

    def test_reset_in_the_past_still_waits_the_minimum(self):
        past = int((self.NOW - timedelta(seconds=30)).timestamp())
        assert self._state(past).reset_at == self.NOW + timedelta(
            seconds=t212_sync.RATE_LIMIT_RESET_MIN_SECONDS
        )

    def test_fractional_reset_value_is_accepted(self):
        reset = (self.NOW + timedelta(seconds=42)).timestamp() + 0.4

RATE_LIMIT_RESET_MAX_SECONDS = 120
RATE_LIMIT_DEFAULT_WAIT_SECONDS = 60

def _reset_at_from_header(raw, now: datetime) -> datetime | None:
    """`x-ratelimit-reset` is documented as a Unix timestamp. Small values are
    still read as relative seconds, and the result is clamped so a misread value
    can never park a run for longer than RATE_LIMIT_RESET_MAX_SECONDS."""
    try:
        value = int(float(raw))
    except (TypeError, ValueError, OverflowError):
        return None
    if value >= _UNIX_MILLISECONDS_FLOOR:
        value //= 1000
    if value >= _UNIX_TIMESTAMP_FLOOR:
        reset_at = datetime.fromtimestamp(value, tz=timezone.utc)
    else:
        reset_at = now + timedelta(seconds=value)
    earliest = now + timedelta(seconds=RATE_LIMIT_RESET_MIN_SECONDS)
    latest = now + timedelta(seconds=RATE_LIMIT_RESET_MAX_SECONDS)
    return min(max(reset_at, earliest), latest)

An account with fewer than 20 pages per stream is not limited at all. ```python
async def _advance_until_blocked(
    db: Session, run, workspace_id: UUID, base: str, api_headers: dict, *, deadline: float,
):
    """Advance `run` repeatedly. Only a step that ended `fetching` (neither
    rate limited nor finished) is followed by another one; the run is re-claimed
    each time because advance_run releases its lease. Returns the last step's
    state with the staged counts of all steps summed."""
    import t212_sync

    run_id = run.id
    lease_token = run.lease_token
    totals = {"orders": 0, "dividends": 0, "cash": 0}
    steps = 0
    while True:
        result = await asyncio.to_thread(
            t212_sync.advance_run,
            db, run, base, api_headers,
            lease_token=lease_token,
            reassert_context=lambda: _set_job_workspace_context(db, workspace_id),
        )
        steps += 1
        totals["orders"] += result.orders_staged
        totals["dividends"] += result.dividends_staged
        totals["cash"] += result.cash_staged
        if (
            result.state != "fetching"
            or steps >= BROKER_BACKFILL_MAX_STEPS_PER_RUN
            or time.monotonic() >= deadline
        ):
            break
        _set_job_workspace_context(db, workspace_id)
        reclaimed = t212_sync.claim_lease(db, run_id, workspace_id)
        if reclaimed is None:
            break  # another worker took the run; it carries on from the checkpoint
        run, lease_token = reclaimed, reclaimed.lease_token
    return replace(
        result,
        orders_staged=totals["orders"],
        dividends_staged=totals["dividends"],
        cash_staged=totals["cash"],
    )

    db: Session, *, drain_seconds: float = BROKER_BACKFILL_DRAIN_SECONDS,
) -> list[dict]:

        results.extend(await broker_backfill_pass(db, workspace_id, deadline=deadline))
    return results

2. **RLS-blind repair SQL** (Task 5 step 2): under forced RLS an `UPDATE` without `portfyl.workspace_id` silently changes zero rows. The repair now sets the context, targets one connection and requires `UPDATE 1`.
3. **Re-walk test in the wrong file** (Task 1): the cash finalize helpers live in `test_t212_finalize.py`, and the existing `test_finalizing_again_imports_nothing_new` only re-finalizes the same run. The new test uses a second run there, and the commit includes that file.
4. **Pagination message never shown** (Task 1): `get_history_status` replaced every `failed` error with a generic "start a new sync to retry", which is wrong advice here. The router now passes `HISTORY_PAGINATION_ERROR` through, and its text no longer says "try again later".
5. **Task 4 cost claim and missing heartbeat**: an idle tick also enumerates workspaces and commits a `job_runs` update; there is no idle log line. The default is 10 s, the comment states the real cost, and the check reads `job_runs.last_success_at`.
6. **Lease check before `failed`** (Task 1): a worker that lost its lease no longer overwrites the run.
7. **Clamp of large relative reset values** (Task 2) is now an explicit, tested behavior change.
